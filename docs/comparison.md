# Comparison

This page sets driftbench beside seven evaluation tools, capability by capability. Every cell of a reference tool carries one source and the date it was read. driftbench cells say what is built today, link to the page that describes it, and end with a proof: the test that fails when the capability breaks.

## Tools compared

* langwatch: the scenario library, [github.com/langwatch/scenario](https://github.com/langwatch/scenario), and its docs at [langwatch.ai/scenario](https://langwatch.ai/scenario/).
* promptfoo: [github.com/promptfoo/promptfoo](https://github.com/promptfoo/promptfoo), docs at [promptfoo.dev/docs](https://www.promptfoo.dev/docs/).
* deepeval: [github.com/confident-ai/deepeval](https://github.com/confident-ai/deepeval), docs at [deepeval.com/docs](https://deepeval.com/docs/).
* inspect_ai: [github.com/UKGovernmentBEIS/inspect_ai](https://github.com/UKGovernmentBEIS/inspect_ai), docs at [inspect.aisi.org.uk](https://inspect.aisi.org.uk/).
* opik: [github.com/comet-ml/opik](https://github.com/comet-ml/opik).
* langfuse: [github.com/langfuse/langfuse](https://github.com/langfuse/langfuse).
* braintrust: docs at [braintrust.dev/docs/evaluate](https://braintrust.dev/docs/evaluate), scorers at [github.com/braintrustdata/autoevals](https://github.com/braintrustdata/autoevals).

## How to read a cell

* `yes`: the cited page shows the capability.
* `partial`: the cited page shows part of it.
* `not found`: the cited page, where the capability would be documented, does not show it. This is not proof that the tool lacks it.
* `not documented in its docs`: no page read for the tool documents it.

All pages were read on 2026-10-11. Tools change; a cell is true of the page on that date.

## Where driftbench is ahead

Four places, each with its evidence. What the other tools do comes from the rows above, read on 2026-10-11. The command output below is what each command printed on the bundled examples, with no model call.

**The block is the unit.** Every exchange is a unit test with its own Given, When and Then. In teacher-forced mode a block runs from its own Given, so it gets a pass rate of its own, free of the blocks before it. The other tools score a scenario run, a test row, a conversation test case, a sample, a dataset item or a trace (row 1). Proof: [schema.test.ts](../packages/core/test/schema.test.ts), [teacher.test.ts](../packages/core/test/runner/teacher.test.ts).

**driftbench checks its own numbers.** Validator ladders prove that a part of driftbench works before its numbers are trusted ([validators](validators.md)). Each ladder scores against a planted truth: faults, recoveries and effects put in at known places, so every result has an exact answer. A ladder runs a bank of at least 300 items in families and tiers. A hardness gate holds a bank back until its pilot forecasts at least 100 iterations to clear it, with at least 100 distinct failing causes. An independent audit then checks four things: a blind pilot, a cheater, a review of the causes and planted bugs. No score is quoted here until a ladder of the current version passes its audit. None of the seven tools shows judge calibration against hand labels in full (row 12).

Proof: [bank.test.ts](../packages/validators/test/bank.test.ts), [hardness.test.ts](../packages/validators/test/hardness.test.ts), [audit.test.ts](../packages/validators/test/audit.test.ts).

**A code agent is tested as an estate.** Its instructions, skills, subagents, guards, tools and settings are read into atoms, approved by a person and turned into tests; recorded sessions replay offline; a mutant deletes one rule so the tests must notice ([testing an estate](estate.md)). Of the six code-agent benchmarks below, none grades office files in the pages read.

```text
$ pnpm driftbench estate mutate examples/estates/fixture/approved.yaml --atom instruction.standing.r3-read-a-file-before-you --delete --to <dir>
Mutant: delete instruction.standing.r3-read-a-file-before-you in CLAUDE.md.
  before: - **R3.** Read a file before you edit it.
  after:  (the line is gone)
  map be2e7a0919cb -> 046d83f242ed
```

Proof: [mutate.test.ts](../packages/estate/test/mutants/mutate.test.ts), [replay.test.ts](../packages/cli/test/replay.test.ts).

**Recovery is measured.** A deviation lands at a chosen block, and driftbench counts the blocks the agent needs to come back, the failures after it and whether the action stayed safe. Among the seven tools, the pages read show part of this for one, through red-team robustness, and none of it for the other six (row 15).

```text
$ pnpm driftbench perturb examples/acme/specs/conversations/plan-upgrade.yaml --class D2_goal_shift --at 2
✓ Recovery: immediate, 0 blocks to come back (the spec allows 1 block), collateral 0, safe action yes, asked first yes.
```

Proof: [recovery.test.ts](../packages/core/test/runner/recovery.test.ts), [perturb.test.ts](../packages/cli/test/perturb.test.ts).

## Tool approval limit for runtimes that run their own tools

Driftbench refuses a denied tool call before it runs wherever the harness runs the tool: the Vercel AI, function and process adapters, and the HTTP chat adapter, where the harness answers each requested tool from the spec. For a runtime that runs its own tools (Nexus, the Claude Code runtime, traces, and SDK loops that own their tool objects), the harness receives the call only after the runtime has run it. The gate then marks the call as denied and fails the block, but the call has already happened. Gating before the call would need each runtime to ask the harness before every call, which none does today.

## Known limits of driftbench's sandbox cleanup

- A process killed with SIGKILL cannot run its cleanup. A workspace folder and a command it started are left behind. SIGTERM, SIGINT and a normal exit are handled.
- A docker container is not stopped when the run ends unclean: docker containers are not part of the exit cleanup. Measured only with a mocked docker command line, since the host this was built on has no docker.

In six rows, none of the seven tools shows the capability in full in the pages read: end state assertions (row 9), judge calibration (row 12), drift across turns (row 14), recovery metrics (row 15), intervals and significance tests (row 17), and multi-language handling (row 28). driftbench covers all six.
